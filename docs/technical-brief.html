Card Fraud · Technical Brief

Catching Fraud That Has No Label Yet

This brief evaluates a Qdrant-based fraud-triage signal for banks: compare each authorization with that cardholder's own past behavior, then send unusual events to analyst review. It needs no chargeback labels, returns a decision in under 14 ms at 11 million transactions, and produces roughly 10,800 false alerts per million authorizations. The takeaway: it can surface new fraud patterns early, but it is a triage signal, not an approve-or-decline fraud engine.

The Labels Arrive Too Late To Help

A supervised fraud model learns from chargebacks, and a chargeback lands weeks after the transaction it describes. For patterns the model has already seen, that lag is tolerable. For a pattern that started last Tuesday it's the whole problem: the fraud runs until enough of it has been labeled to retrain on, and only then does the model see it.

The alternative tested here is a per-cardholder behavioral baseline, which needs no labels at all. Not "does this look like known fraud" but "does this look like this cardholder". Every customer supplies their own training data by transacting normally, so the signal is available on day one of a new pattern rather than six weeks in.

The Score Is A Ratio, So One Threshold Fits Every Customer

Each transaction becomes one 31-field behavioral profile, stored in Qdrant as a vector: amount, currency, hour of day, day of week, merchant category, channel, distance from the cardholder's home city, whether the merchant is new for this cardholder, and five values describing the recent history (minutes since the last charge, same-merchant count in the last 10 minutes, implied travel speed, amount against the recent median, and the length of any run of escalating charges at one merchant).

Scoring compares the new transaction profile with only that cardholder's prior transactions:

score = d_event / d_local d_event mean distance from the event to its 10 nearest neighbors inside this cardholder's history d_local mean distance of those 10 neighbors from their own centroid

The ratio adjusts for how varied each cardholder's normal spending already is, which is why one threshold can work across customers. A cardholder who always spends 40 EUR at three merchants has a tight neighborhood, so a 120 EUR charge in a new city is far in relative terms. A cardholder whose normal life already spans 200 EUR to 4,000 EUR has a loose neighborhood, and the same absolute distance sits comfortably inside it. Both produce comparable ratios, so a deployment maintains one number rather than 80 million.

What Qdrant Does For Each Authorization

The demo stores every cardholder's history in one Qdrant collection rather than one collection per customer. Each record carries a tenant_id indexed with is_tenant: true, which tells Qdrant to store a cardholder's records together so reading them is sequential. The collection uses Qdrant's documented multitenancy setting for this layout, m: 0 with payload_m: 16: Qdrant builds its search structure inside each cardholder's group instead of one global graph over the whole collection.

Scoring an authorization is two reads and one write:

  • Recent History. A filtered scroll for the cardholder's 30 most recent points, newest first, which supplies the five recent-history features.
  • Nearest Neighbors. A search within that cardholder's history: it takes 100 candidates, ranks recent behavior higher, and returns the 10 closest matches with their vectors.
  • The Write Happens After The Decision. The scored event is persisted so the next authorization can see it, but nothing in the approve-or-decline path waits on it. Every latency number in this brief excludes it.

Qdrant narrows the search to the cardholder while it searches, not after it has searched the full collection, so a query reads one cardholder's few hundred records instead of scanning the collection and discarding almost all of it. That is what keeps the cost of a query tied to one customer's history rather than to the size of the collection around it, and the sweep later in this brief is what it looks like measured.

In a bank the recent-history read comes from the feature store or cache that already exists, which leaves a single filtered vector search on the decision path.

Each Alert Keeps Its Evidence

Each alert stores the 10 prior transactions it used as comparisons, d_event, d_local, and a plain-language explanation. An analyst opening the case in March reproduces the exact arithmetic from February, on the neighbor set as it stood at scoring time, rather than on whatever a fresh search would return now. For model governance that reproducibility carries as much weight as the latency does.

On Isolation, Precisely

Every query carries a tenant filter, and tenant_id is indexed with is_tenant: true so each cardholder's vectors are co-located. evals/tenant-isolation.ts asserts that no neighbor returned on any of the system's query paths belongs to another cardholder.

That is query-level isolation, not a hard storage boundary. Where a hard boundary is the requirement, Qdrant's own exception is separate collections with per-tenant encryption, under a limit of roughly 1,000 collections.

What It Costs At Real Prevalence

That precision is measured on a stream where 5.2% of events are fraud. Real card fraud runs near 0.1% of authorizations. Recall and the false-positive rate hold across that change; precision does not, because its denominator is dominated by normal traffic that grows a hundredfold. Read the false-positive rate as conditional. It was measured on synthetic background traffic, not on bank authorizations, so projecting it onto 999,000 real transactions is an estimate that inherits whatever that traffic gets wrong about real cardholders. Calibrating it against a sample of live authorizations is the first thing a deployment should do.

At production prevalence an unlabeled outlier signal sends mostly false alerts, roughly 95% here, which is why this belongs in front of an analyst queue rather than in front of an approve-or-decline. Read as triage it's a reasonable trade: about 11,000 items a million to review, against 192 fraud cases that carried no label anyone could have trained on.

Latency Tracks Cardholders, Not Transactions

Decision latency is the recent-history scroll plus the neighbor search, including the local feature encoding between them. The write is excluded. Each cell loads a fresh collection, waits for the optimizer to settle, discards 100 warm-up events, then measures 1,000 authorizations one at a time.

The benchmark has two groups, and they should not be compared against each other. A cell with fewer cardholders than samples has to touch each cardholder more than once, which measures a warm segment; a cell with 1,000 or more cardholders measures a cold first touch every time, which is the production case, since an issuer's next authorization comes from an arbitrary cardholder. Both groups grow the collection tenfold, and they disagree about what it costs. Holding cardholders at 200 and giving each one 15 months of history instead of three moves the median from 8.95 ms (repeat: 8.65) to 7.96 ms (repeats: 8.54, 8.40). If the forced graph build adds any overhead, it lands on the 0.11 M cell, so this comparison can only err against the smaller collection. Holding history at three months and going from 2,000 cardholders to 20,000 moves it from 8.27 ms (repeats: 8.99, 9.17) to 13.51 ms (repeat: 13.85).

The same tenfold in points costs nothing one way and about 5 ms the other, so the transaction count is not the driver. The number of cardholders is. The split between the two reads says the same thing: the payload-filtered scroll goes from 4.53 to 7.98 ms across that step while the vector search moves only from 3.77 to 5.57 ms. Growth is landing on the filter, not on the graph traversal.

The Multitenant HNSW Config Makes No Measurable Difference Here

At 1.1 million points the two configs are too close to separate. Three runs with m: 0, payload_m: 16 gave medians of 8.27, 8.99, and 9.17 ms against 9.21, 8.43, and 9.67 ms for Qdrant's default global graph. The multitenant median is lower, at 8.99 against 9.21, but the two sets interleave and the gap is smaller than the spread within either one. Read that as no measurable difference at this size, not as a small win.

At 11 million points, two runs per configuration show the same result. The multitenant config scored 13.51 / 17.57 / 21.24 ms and 13.85 / 19.84 / 26.35; the default global graph scored 13.26 / 16.13 / 20.74 and 15.55 / 23.63 / 34.52. The four runs interleave. The 34.52 ms p99 default run was the outlier. It ran on a Docker storage volume degraded by repeated 11-million-point load and delete cycles; after the volume was wiped, its repeat produced the fastest run of the four. The load-and-index times point the same way: the outlier took 26.9 minutes where the other three runs took 18.5 to 20.3. An earlier draft read that outlier as the config separating at this size. The repeats say the spread is storage state, not graph configuration. The multitenant config stays the shipped choice because it is what the multitenancy documentation prescribes for payload-partitioned collections, but no latency number in this brief depends on it.

The Threshold Is Calibrated To History Depth

One result from the sweep belongs in any retention decision. The alert threshold of 2.0 was tuned against cardholders holding roughly three months of history. On the 15-month cell, where each cardholder holds 5,472 points instead of 547, 2.5% of ordinary transactions clear that same threshold, reproducibly at exactly 25 of 1,000 across three runs.

The reason is the ratio. Denser history puts a cardholder's 10 nearest neighbors closer together, which shrinks d_local, and a smaller denominator lifts the score for an unchanged transaction. A deployment that extends its retention window has to recalibrate the threshold against the new depth, or watch its false-positive rate climb for reasons that have nothing to do with fraud.

The benchmark flags that cell because of those alerts. An alerted event is persisted even when the benchmark asks for no writes, so the 15-month cell wrote 25 points during its measurement and the harness marks it accordingly. Those 25 points land across 200 cardholders holding 5,472 points each, roughly one extra point per eight cardholders, which is too small to move a latency median. The flag is reported here rather than suppressed, and the reading it produced is used.

Where This Sits In A Real Fraud Stack

Banks already use per-cardholder behavioral profiling in issuer fraud stacks. It answers the question "does this look like this cardholder". This brief shows one way to implement that question with Qdrant, with the cost of every query tied to one cardholder's history rather than to the size of the collection.

The latency fits the envelope it would have to live in. A card authorization runs on an end-to-end budget of a few hundred milliseconds, and the risk-scoring slice of that budget is typically tens of milliseconds. A 13.5 ms median at 11 million points, measured on a laptop over loopback, sits inside that slice with room left for the network hops a production deployment adds.

What This Is Not

  • A Fraud Engine. This is one signal for fraud patterns without labels. It feeds an analyst queue alongside the rules engine and the supervised model; it replaces neither.
  • A Full Feature Set. A production issuer runs hundreds of features through gradient-boosted trees, plus rules, plus consortium signals. A nearest-neighbor outlier ratio on 31 hand-weighted features is one input among those.
  • Real Data. Every number here is measured on a generated world of cardholders and generated fraud sequences. No consortium data, no device fingerprinting, no supervised training.
  • A Closed Loop. There are no chargeback labels and no analyst dispositions flowing back. Real deployments retune on both.
  • A Throughput Benchmark. Per-query latency was measured; sustained throughput under concurrent load was not. The benchmark ran on a laptop over loopback rather than on server hardware.
  • A Distributed Test. Qdrant documents payload-based partitioning as scaling to roughly 10,000 tenants, past which the answer is custom sharding by tenant key and promoting large tenants to dedicated shards. That recommendation comes from Qdrant's documentation, not from anything measured here.

At 80 million cardholders the shape of the deployment changes: a rolling retention window rather than unbounded history, tiered multitenancy, and sharding by cardholder key. The sweep establishes which of those levers matters. Retention depth is close to free, so a longer window is affordable as long as the threshold is recalibrated for it. Cardholder count is what the cost tracks, and sharding by cardholder key is the documented answer to that.
